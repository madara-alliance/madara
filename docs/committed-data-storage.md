# Committed-data storage and replication

Madara stores each immutable dataset under its Merkle root in the existing RocksDB metadata column family. A dataset import computes and checks the root before writing. All value pages, internal-node pages, and metadata are written in one batch with a synchronous write-ahead log; an acknowledgement means the dataset is durable. Re-importing the same root rewrites its authenticated pages and preserves the first-import checkpoint.

The key format is `committed_data_pages/ | root (32 bytes) | level (1 byte) | page (4-byte big-endian)`. Level 0 holds raw felt values; higher levels hold internal Poseidon nodes. Each RocksDB page holds at most 256 canonical, 32-byte felts. Level 255, page 0 is the metadata record: count (4 bytes), minimum tree height (1), checkpoint-present flag (1), and confirmed-head checkpoint (8). The checkpoint records the local confirmed head when the root was first imported. It does **not** identify the block that published or last read the root, so it cannot by itself drive block-based pruning.

Only occupied nodes are stored. Witness reads fetch the leaf and one sibling per tree level from those pages; missing right siblings use deterministic zero-subtree hashes. Missing metadata or an unused index returns no witness. Missing or malformed pages are errors. The consumer must verify the reconstructed witness against the requested root.

The feeder gateway lists up to 64 complete roots per response and serves at most 4,096 values per page. These are wire-protocol constants shared by the producer and syncing client, not operator settings. A full node assembles every page, recomputes the root, and only then imports the dataset. Root listing uses a lexical cursor; a syncing node rescans because imports can arrive below an earlier cursor. No dataset size quota or pruning policy is enabled. Future pruning requires a separate, authenticated mapping from roots to publishing/usage blocks and must account for historical reads and proof generation.
